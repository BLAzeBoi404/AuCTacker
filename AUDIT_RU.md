## Другие исправления

- Денежные поля PostgreSQL переведены с `integer` на `bigint`: суммы более 2 147 483 647 сохраняются без переполнения. На входе проверяются безопасные целые значения.
- Старые записи сохраняются. Миграция добавляет поля редкости, времени исчезновения и диагностики. Старые трекеры покупки остаются в режиме «точно»; для «от и выше» создайте трекер с новым режимом.
- Исправлена очередь Telegram: отложенная повторная попытка не теряется, даже когда активных трекеров уже нет. Перепривязанный к другому профилю чат не получает чужое старое уведомление.
- Смена статуса продажи и создание уведомления выполняются одной транзакцией. Начальный снимок покупок и переход в состояние исчезновения сохраняются сразу, чтобы не теряться при перезапуске.
- Добавлены тайм-ауты Telegram, криптографические коды привязки, атомарное использование кода и защита от одновременной обработки входящих обновлений в одном процессе.
- Кэши ограничены по размеру, объединяют параллельные запросы и не возвращают устаревшую запись после сброса. Небольшой аукцион загружается одним запросом вместо заранее отправленных лишних страниц.
- Сохранён регистр ID предмета. Обновление токена доступа объединяет одновременные запросы. Адрес EXBO можно переопределить через `EXBO_API_BASE_URL`.
- Исправлено появление графика после первоначально пустых данных, расчёт статистики за штуку и отображение неизвестной заточки.
- Убрано глобальное подавление необработанных исключений. Фоновые задачи по-прежнему обрабатывают свои ошибки локально.
- `src/middleware.ts` заменён на `src/proxy.ts` по соглашению установленной версии Next.js.

## Как определяется исчезнувшая продажа

Один пропуск не завершает слежку. Нужны минимум две успешные проверки отсутствия. До известного срока окончания неполная выдача EXBO не считается исчезновением. После окончания предусмотрен запас 15 минут для обновления данных.

Если срок неизвестен или лот снят раньше, после 30 минут подтверждаемого отсутствия он переходит в «Лот исчез». Продажей это не объявляется. При найденной подходящей сделке проверяется её дата, поэтому продажа может быть распознана и после простоя сервера.

Публичная история не доказывает принадлежность сделки конкретному продавцу. Совпадения неоднозначных сделок и отсутствие метаданных не дают надёжного подтверждения; в таких случаях следует проверить результат в игре.

## Обновление проекта

1. Распакуйте архив в новую папку проекта или замените исходники в рабочем репозитории. Сохраните свой `.env` и переменные окружения хостинга.
2. Если копируете поверх старой папки, удалите прежний `src/middleware.ts`: теперь используется `src/proxy.ts`.
3. Выполните `npm ci`, затем `npm run build` и `npm run start`.
4. При запуске сервер автоматически выполнит миграцию существующей базы. Новые поля не требуют удаления старых трекеров.
5. Проверьте, что фоновая слежка включена и Telegram привязан. Для работы слежки процесс сервера должен работать либо регулярно запускаться внешним cron. Остановленный процесс не может разбудить себя своим таймером.

Для повторения проверок:

```bash
npm ci
npm run typecheck
npm run lint
npm test
npm run build
npx playwright install chromium
npm run test:ui
```

`AUCTRACKER_BACKGROUND=0` предназначен для локальной проверки без фоновых обращений. В рабочем окружении его не устанавливайте, если нужен встроенный планировщик. Эта переменная не отключает явные действия пользователя через API.

В архив не включены `node_modules`, `.next`, тестовые снимки, рабочие секреты и локальная база.

## Ограничения данных EXBO

Если API не передал редкость, восстановить её по цене нельзя. Такая сделка остаётся в общей истории как «Неизвестна» и не попадает в фильтр конкретной редкости. Это устраняет ошибочную подпись «Обычный», но не добавляет отсутствующие у источника данные.

История и список лотов загружаются с ограничением количества записей. Интерфейс сообщает, когда показана лишь часть; фильтрация применяется к загруженным данным. Новые лоты и продажи могут появляться в API с задержкой.

Кэши и защита параллельного запуска находятся в памяти процесса. Проверенная конфигурация — один постоянно работающий экземпляр приложения. Несколько независимых реплик потребуют общего механизма блокировок фоновых задач.
